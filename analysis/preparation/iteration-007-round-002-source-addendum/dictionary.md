## business-config.json

`configs` — массив версий. Составной ключ: config_id+version+comparison_group_id+root_scope+valid_from+valid_to. `owner/approved_at` — независимое проспективное утверждениеv1; v2 помечена change_reason/supersedes_version и утверждена после valid_from. `work_type/unit/target_value/baseline_value/direction/target_basis` — рабочая цель и её основание. Отсутствующий baseline=null не заменяется результатом из старогоbase. Потоковая цель следует из мощности/классификатора; workflow100 из плана100запусков; analytical1 из одного заранее назначенного решения.

`acceptance_criteria/use_criteria` — проверяемые требования к рабочим подтверждениям, `business_deadline` — деловой срок, `maturity_end` — горизонт наблюдения. `source_query` описывает используемые таблицы, период и смысл связи: joins применяются лишь к таблицам, где соответствующие поля существуют; case→root берётся из work_events, deliverable из project_records. Это описание выборки, не программный SQL. Scope охватывает **все** назначения; самоотбор удобных случаев запрещён содержанием рабочего плана.

`readiness_criterion.ready_by` для аналитики — конкретный срок единственной предрассылки; rationale объясняет деловую пользу до заседания, further_earliness_benefit=none_assumed. `comparison_rule` задаёт одинаковые тип/период/плановую мощность/инженерный mix, аналитические пакеты сравниваются в своём типе. `qa.criterion/scale/scale_version/unit` — совместимость; precision_points=1 и substantive_difference_points=1 — практическая точность делового измерения и граница содержательного различия, а не правила награждения. minor/major/critical_penalty — интерпретация исходной шкалы.

`CFG-LEGACY-*`: отдельные группы G-support/backoffice/project, target108/80/100 с тем же grain/period/scope, применимы к неизменным старым source-полям. application_scope=round002_prospective_common_assumption_only и does_not_amend_legacy_source_rule=true отделяют новое сценарное требование от исторических правил. На R4 и на analytical для legacyG-project соответствия нет. `business_configs` возвращает массив совпадений по группе/периоду/типу/версии; [] — явное отсутствие, несколько записей без типа — явная неоднозначность, не автоматический выбор первой. Эта функция не проверяет людей и не вычисляет их показатели.

## Patch / index / reader

Index: name, source=addendum, source_ref, baseline, alternative_snapshot=true, необязательный patch_ref. Внешний старый index читается отдельно и даёт source=old. Patch: name, operations. Операции прежние update/insert/delete/append_export_copy с table/grain/key/set/row. Добавлена чисто транспортная `reorder`: table/grain/key={}, keys — каждый текущий PK ровно1раз; она восстанавливает исходный порядок массивов после вставок/удалений для буквального SHA. Порядок не является признаком результата. Reader не угадывает значения, не импортирует генератор и не читает другие каталоги.
