# Итерации решения кейса


Координатор — основной агент текущего чата. Этот skill организует работу custom agents, а не запускает внешний сервис или расписание. Создание конфигурации и обсуждение не являются запуском. Пользователь пока отложил реальную работу.

## Запуск и входы

1. При прямом поручении запустить `$case-iteration` прочитай проектные инструкции, `project/status.md`, [протокол](references/protocol.md) и [контракты](references/contracts.md). Параметры по умолчанию — [run-config.json](assets/run-config.json); запрос пользователя имеет приоритет.
2. Требуются проверенные условия, пакет доказательств, диагностика и описание текущей программы. Если подготовленной wiki или явно назначенного входного пакета нет, верни `needs_inputs`. Не запускай `knowledge-curation` автоматически: для него сохраняется отдельное поручение.
3. Диагностику выполняет `case-analyst` через `$case-diagnosis` один раз, затем обновляет только по новой задаче/данным. Источники и отзывы не анализируются заново в каждом цикле. Точечные пробелы поручай `evidence-researcher` через `$evidence-check`.
4. Подготовь небольшой самодостаточный входной пакет по контрактам. Зафиксируй источники и версии, не копируй всю библиотеку. Создай запуск и раунд командами [snapshot_store.py](scripts/snapshot_store.py), только после разрешённого запуска workflow.

## Один цикл

1. Поручи `iteration-planner` создать plan.json: две независимые задачи, основания различия, гипотезы, критерии улучшения/отказа, нужные проверки. В первом цикле каждая ветка предлагает две концепции; далее по одной. Если разумнее сначала проверить критический факт, выполни ограниченную проверку до генерации и заморозь обновлённые входы.
2. Создай два экземпляра `concept-developer`, по одному на ветки A/B. Передай общий замороженный пакет, отдельное задание и отдельную область записи. Поручи `$concept-design`; не показывай им текущие результаты друг друга. Дождись обоих результатов, не заменяя потерянный результат выдуманным.
3. По необходимости один раз верни конкретные исправления в рамках раунда. Предел локальной доработки задан в конфигурации; дальнейшее изменение механизма становится новой версией следующего раунда.
4. Поручи `financial-analyst` через `$case-finance` проверить все варианты на одинаковых основаниях; `evidence-researcher` или основной агент через `$evidence-check` проверяет значимые утверждения. Исправление фактической основы требует новой версии входов, доступной всем вариантам.
5. Подготовь review-packet с псевдонимами V01…: концепции, доказательства и расчёты, без авторов, прежних рангов, истории побед и lineage. Включи текущую программу как baseline; со второго цикла включи неизменённого предыдущего победителя. Приватную карту держи отдельно от назначенных reviewer входов. Это инструкция контекста, не техническая изоляция файлов.
6. Поручи свежему `concept-reviewer` применить `$concept-review`: сначала независимая оценка по замороженной рубрике, затем допускается сравнение изменений. Reviewer вправе отклонить все варианты. Не заставляй его назвать победителя и не запускай новый reviewer ради желаемого ответа.
7. Разбери замечания и обоснованный шортлист. Выбор и интеграция — ответственность координатора. Для комбинации разных механизмов нужна отдельная проверенная версия, а не копирование лучших обещаний.
8. Сохрани selection.json и delta.md: фактическое изменение, основания выбора, ограничения и наличие содержательного улучшения. При изменившихся входах нельзя заявлять улучшение на одинаковой базе; укажи контекст изменения и перепроверь прежнего победителя.
9. Проверь и запечатай снимок. Технический валидатор подтверждает структуру, версии и заявленные gates, но не истинность выводов и не исполнение бюджета в реальном банке.

## Повторение и завершение

Передай планировщику компактные итоги, не весь журнал работы. После первого цикла обычно одна ветка улучшает текущий лучший вариант, другая проверяет конкурирующий механизм; планировщик обосновывает другой выбор при критическом пробеле.

Завершай при лимите циклов/ресурса, двух циклах без содержательного улучшения по умолчанию, отсутствии полезной следующей проверки, запросе пользователя остановиться или отсутствии необходимых инструментов. Не сбрасывай счётчик циклов созданием нового run ради обхода лимита. Статус ресурса считай только по доступным измерениям: не выдумывай расход токенов.

Для продолжения сначала проверь целостность запечатанных снимков. Незавершённый раунд продолжай, не перезаписывая результаты; ошибки и прерванные ветки отражай честно. Закрытые снимки не редактируй.

Финальный отчёт: лучший допустимый вариант либо честное отсутствие победителя, сравнение с baseline/предыдущим результатом, доказательства, проверки, остающиеся допущения и путь к снимку. Презентацию собирай через `$case-storyline`, если финализация входит в поручение. Файл не отправляется организаторам автоматически.
