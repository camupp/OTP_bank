# Перенос CryptaId Storage из Reactor/Spine в Logos

Перенеси существующий сервис `crypta/graph/cryptaid_storage` на Logos: подготовь реализацию, интеграцию в граф, тесты и проверяемый diff. Сохрани вычисления, накопленные данные, даты и интерфейс для потребителей. Подготовь порядок переключения и отката, но само production-переключение в эту задачу не входит.

Ниже приведён контекст исследования сервиса на 28 октября 2026 года. Это стартовая карта, а не замена чтению актуального кода. Перед изменениями сверь сведения с текущим checkout, индексом trunk и ближайшими `AGENTS.md`. Фактические запуски и состояние production-таблиц в рамках исходного исследования не проверялись.

## 1. Цель и границы работы

Нужно перенести **один регулярный расчёт таблицы `activity`**. Сейчас это Python-бинарник с YQL-запросом, запускаемый Reactor через Sandbox bundle. В исходном сервисе нет дерева Luigi-классов.

В YQL определены `$init_state` и `$update_state`. Это две ветки одного расчёта, а не две независимые ежедневные задачи:

- `init_state` — начальное заполнение при отсутствии выходной таблицы;
- `update_state` — обновление накопленного состояния.

По умолчанию оставь одну вычислительную задачу с этими режимами. Отдельная разовая bootstrap-процедура допустима, только если она нужна для корректной интеграции с Logos и её роль обоснована. Production не должен запускаться с потерей существующей истории.

Целевой Logos-проект — `logos/projects/crypta_matching/`. Подтверди соответствие по текущим соседним задачам. Не используй `crypta_indevice` или `crypta_profile` только из-за сходства отдельных зависимостей.

Предпочтительное размещение реализации — `crypta/graph/cryptaid_storage/logos/`, с сохранением пригодной общей вычислительной библиотеки и SQL-ресурса. Не навязывай структуру `tasks/`, интерфейс `run_process()` или доменный базовый класс из другого проекта.

Рабочие имена классов: `CryptaIdActivityProductionTask` и, если позволяет текущая модель окружений, `CryptaIdActivityTestingTask`. Это предложение: сверь соглашения соседних реализаций и зафиксируй итоговую карту имён. Не регистрируй абстрактную общую задачу как дополнительный writer.

Не расширяй работу до переноса Сеятеля, Мичурина, graph-v1, всего IDs Storage, публикации всех таблиц Crypta или BigB.

## 3. Назначение сервиса и семантика данных

`activity` — накопительная таблица с полями:

| Поле | Смысл |
|---|---|
| `crypta_id` | Идентификатор группы склейки в человека |
| `date_begin` | Первая известная дата присутствия ID в используемой истории графа |
| `date_end` | Последняя известная дата присутствия ID |

Здесь активность означает присутствие Crypta ID в данных графа, а не непосредственно дату последнего визита пользователя или события в логах. Сервис не сохраняет все интервалы присутствия, число активных дней и историю изменений состава группы.

Источник — выгрузка `mi-ext`: результат Сеятеля, который расширяет граф Мичурина `mi` оффлайн-рёбрами из подготовленного СУПа. Этот upstream переносить заново не требуется.

## 4. Точный контракт runner и YQL

### 4.1. Даты

Legacy runner на каждой попытке вычисляет:

```python
run_date = time_utils.get_current_utc_datetime().strftime("%Y-%m-%d")
vertices_generate_date = get_generate_date(yt_client, config.Vertices)
```

Сохрани различие:

- `run_date` — UTC-дата фактической попытки запуска; фиксируется для этой попытки, не кешируется на весь процесс;
- `generate_date` — строковый атрибут `vertices/@generate_date`, переданный в YQL;
- `ctx.task_dt` / Reactor `user_time` — логическая дата задачи; она не становится автоматически датой данных или фактического запуска;
- `date_begin` / `date_end` — значения в строках, а не атрибуты всей таблицы.

Для запуска 28 октября с входом за 27 октября корректно получить `run_date=2026-10-28`, `generate_date=2026-10-27`. Не добавляй механический `shift=-1`: legacy читает атрибут источника, а не вычитает сутки.

В legacy `get_generate_date()` возвращает `"0000-00-00"`, если атрибута нет. Отсутствие самой входной таблицы вызывает ошибку чтения. Не заменяй это сегодняшней датой или новой валидацией без отдельного обоснования изменения поведения.

### 4.2. Пропуск повторного расчёта

Точный guard:

```python
activity_exists and activity_generate_date == vertices_generate_date
```

При выполнении guard YQL не запускается, а данные и legacy-атрибуты `activity` не переписываются. Проверяется равенство дат, а не условие «вход новее выхода». Изменение содержимого вершин при прежнем `generate_date` не вызывает пересчёт.

Особенно проверь обвязку Logos: успешный no-op не должен через post-processing перезаписать `activity/@generate_date` логической датой задачи, поменять `@run_date` или создать ложное сообщение о свежих данных. При этом последующий потребитель и сам Logos должны корректно воспринимать завершение попытки. Выбери штатный механизм, не меняя общую библиотеку Logos ради одной задачи.

### 4.3. Первое заполнение

Если `activity` отсутствует, запрос читает `RANGE(internal)` и `RANGE(delta)` без границ дат, объединяет строки через `UNION ALL`, исключает пустые `cryptaId` и вычисляет:

```text
date_begin = MIN(date)
date_end   = MAX(date)
```

Получается одна строка на `crypta_id`, отсортированная по нему. В этой ветке строки текущей `$vertices` не читаются и не добавляются. Однако runner всё равно читает `vertices/@generate_date` и записывает эту метку в выход.

Не ограничивай архив скользящим окном, логической датой Logos или произвольным allowlist таблиц. Не объединяй bootstrap с дополнительным обновлением по текущим вершинам: это изменит legacy-результат.

Для первого production-запуска Logos используй существующее накопленное состояние. Bootstrap из архива нужен как поддерживаемый режим и тестовый сценарий; он не оправдывает удаление production-таблицы. Полнота доступного архива и полнота уже накопленной истории — разные вопросы.

### 4.4. Регулярное обновление

Если `activity` существует и guard не сработал:

1. Из текущих вершин выбираются непустые `cryptaId`.
2. Создаётся физическая временная `@new_activity`, где обе даты равны входному `generate_date`.
3. Новые наблюдения объединяются со всей существующей `activity`.
4. Для каждого ID выбираются `MIN(date_begin)` и `MAX(date_end)`.
5. Итог целиком перезаписывает `activity` с нужными пользовательскими атрибутами.

Сохрани следующие свойства:

- новый ID получает обе даты, равные дате входных данных;
- существующий ID сохраняет самую раннюю дату;
- исчезнувший из текущих вершин ID остаётся в накопленной таблице;
- повторно появившийся ID сохраняет историю и обновляет последнюю дату;
- дубликаты вершин не создают дополнительные итоговые строки;
- в запросе нет удаления истории по возрасту.

### 4.5. Схема, атрибуты и оптимизация

Сохрани имена и фактические типы колонок, optionality, сортировку по `crypta_id` и атрибуты `run_date` / `generate_date`. Сверь их с тестовыми схемами и реальным выходом. Не превращай даты в timestamp и не переименовывай `cryptaId` во входном контракте.

В актуальном YQL важны:

- `@new_activity` с последующим `COMMIT`;
- `Just($generate_date)` для согласования optional-типов;
- `GROUP COMPACT BY crypta_id`;
- `ASSUME ORDER BY crypta_id`;
- отсутствие дополнительного key-фильтра над итоговым `UNION ALL`.

По комментариям автора это сохраняет эффективный план на отсортированных входах. Не заменяй код старой локальной версией с обычным `GROUP BY` и дополнительной сортировкой; не проводи попутную оптимизацию или форматирование всего SQL. Сохрани ключ ресурса `/query/activity.sql`, если нет реального конфликта.

## 5. Восстановить контракт оркестрации

Из исходного Spine известны:

| Настройка | Legacy-значение |
|---|---|
| Запуск | Ежедневный cron `0 0 3 ? * * *` |
| Окружения | production и testing |
| Ограничение выполнения | 18 часов |
| Повторы | `max_retries=3`, интервал 2 часа |
| Проверка успешных запусков | `crit_time=49h` |
| Идентификатор проверки | `crypta-graph-cryptaid_storage-{env}` |
| Bundle | `crypta-graph-cryptaid_storage` |

Пути старых реакций:

```text
/crypta/matching/cryptaid_storage/production/calculate_crypta_id_storage
/crypta/matching/cryptaid_storage/testing/calculate_crypta_id_storage
```

Часовой пояс cron в сервисном коде явно не задан. В исходном исследовании он не был надёжно подтверждён. Установи его по авторитетной конфигурации/документации Reactor или проверенному расписанию; не объявляй `03:00` ни UTC, ни МСК без проверки.

Проверь effective queue, semaphore, обработку задержанного cron, последовательность запусков и число одновременно работающих writers. Сохрани защиту накопленного состояния от параллельной записи. Новый семафор Logos сам по себе не блокирует старый Sandbox writer.

`49h` — порог давности успешного завершения, а не `exec_time`, TTL, retention или проверка `vertices/@generate_date`. `.add_yt_dependencies(YtProxy.Group.offline)` относится к подавлению мониторинга при обслуживании YT и не означает ожидание готовности вершин.

Вырази расписание средствами целевого Logos-графа. Не своди перенос к запуску прежнего CLI из новой оболочки. Если расписание по готовности Сеятеля вместо прежнего cron полезнее, сначала покажи, как это меняет дату входа, задержки и повторы; не внедряй такое изменение незаметно.

Разделяй `exec_time` для оценки лага и Nirvana `ttl` для жёсткого ограничения. Не устанавливай `exec_time=49h` и не выводи его из формулы `ttl / 2`. Сохрани известный legacy-лимит времени; оценку длительности бери из наблюдений или текущих правил графа, явно указывая отсутствие измерений.

## 6. Зависимости, логтайпы и окружения Logos

Перед новыми объявлениями выполни поиск существующих логтайпов через registry/`find_logtypes` и прочитай их определения. Не создавай дубликаты из-за разных текстовых alias одного объекта YT.

Известны два важных существующих определения:

- `CryptaSowerVerticesNoMultiProfileByCryptaId` в `logos/logs/cryptais/CryptaSower.py`;
- `CryptaPublicIdsStorageCryptaIdActivity` в `logos/logs/cryptais/CryptaPublicIdsStorageCryptaIdRegions.py`.

У первого при исследовании был путь с `/matching/workdir/vertices_no_multi_profile_by_crypta_id`, а legacy читает `/matching/vertices_no_multi_profile_by_crypta_id`. Подтверди producer и связи/aliases этих путей. Не считай их одинаковыми только по имени таблицы.

У второго публичный путь `//home/crypta/public/ids_storage/crypta_id/activity`, Kolmogorov и `external=True`. Это не автоматически подходящий output producer-задачи, которая пишет в production-путь. Проверь отношение public/production, links, публикацию и владельца таблицы; не меняй публичный логтайп вслепую.

Для каждого используемого объекта зафиксируй: логтайп, физический путь, окружение, кластер, producer, ownership, тип готовности и участие в bootstrap.

Legacy читает доступный mutable singleton вершин, не ожидая конкретного дня. `LastTableDependency` подходит только при сознательном сохранении такого latest-контракта и не создаёт ожидания сегодняшнего producer. `SingleTableDependency` или событие готовности требуют обоснованного соответствия дат. Не добавляй автоматический сдвиг на вчера.

Накопленная `activity` — persistent state, который одновременно читается и обновляется. Выбери штатную модель Static/state/output. Не создавай два output-лога на один физический путь и не вводи зависимость от отсутствующего предыдущего дня, блокирующую bootstrap.

Архив нужен только для начального заполнения. Не превращай его без необходимости в обязательную многолетнюю зависимость каждого ежедневного обновления и не меняй область `RANGE`. Обеспечь явную подстановку архивных путей для dev и тестов, даже если они остаются runtime-настройками, а не обычными daily dependencies.

В `run()` бери объявленные пути из `inputs` / `outputs`; все остальные runtime-пути тоже должны корректно изолироваться. Не конструируй production-пути вручную поверх подмен Logos. Разделяй Crypta environment, Logos graph type и `ctx.test_mode`.

Сохрани поддержку существующего testing-сценария, но проверь текущий статус `PREPROD_TASKS`. При исследовании часть PREPROD-регистрации графа была выключена. Подготовка testing-класса не разрешает активировать остановленный PREPROD или отключить старый testing scheduler без работающей замены.

## 7. Runtime, транзакции и повторы

Предпочтительная основа — `logos.BaseLogTask` или принятый соседями совместимый класс. Здесь есть runtime-проверки существования и метаданных, поэтому не выбирай автоматически `BaseYqlTask` только из-за одного SQL-файла. Обоснуй окончательное решение по текущему API.

Клиенты получай из `services.yt` / `services.yql`. Переиспользуй вычислительный код, если можно отделить создание клиентов от расчёта без лишнего framework. Не импортируй Logos в универсальную библиотеку ради простой передачи клиентов.

До реализации выбери и опиши владельца YT-транзакции:

- либо транзакция Logos и тот же id передаётся запросу;
- либо явно совместимое собственное управление, если оно действительно необходимо.

Не оставляй две независимые внешние транзакции, не отключай output locks/валидации по аналогии с Сеятелем: у него другой многошаговый контракт.

Для state обязателен режим без удаления выхода перед запуском: сохрани `drop_outputs_before_run=False` и проверь фактический порядок действий TaskRunner. Наличие `WITH TRUNCATE` в SQL не разрешает удалять старую таблицу до чтения её истории.

Внутренний `COMMIT` после `@new_activity` — граница этапов YQL. Он не должен приводить к преждевременной публикации накопленного состояния или потере rollback внешней транзакции. Проверь это на реальном YT/YQL-сценарии, а не только моками.

Проверь совместимость legacy `generate_date` с post-processing и валидацией Static-выходов Logos: логическая дата задания может отличаться от даты вершин. Используй штатную настройку с минимальным обоснованным изменением проверок. Не отключай одновременно все гарантии и не правь `logos/libs` ради обхода локальной проблемы.

Проанализируй гонку между чтением `vertices/@generate_date` и чтением строк mutable source. Если для корректного переноса нужен snapshot или проверка версии, реализуй минимальный механизм и отдельно опиши отличие от legacy. Не заявляй о гарантии snapshot, если её нет.

Для обычных попыток и retries сохрани чтение доступной версии на момент попытки. Отдельно определи допустимость запоздалого слота и production `RECALCULATE`: текущий singleton и накопленное состояние не дают автоматической возможности восстановить исторический срез. До введения поддержки не разрешай историческому режиму незаметно менять live-state. Не копируй политику просроченных запусков из Klondike или Auto Guidebook без анализа этого сервиса.

## 8. Потребители и события

Проверь найденного потребителя:

```text
logos/projects/bigb/tasks/merge_public_profiles_with_crypta_task/__init__.py
```

`BigbMergePublicProfilesWithCryptaTask` читает публичную `activity` через `LastTableDependency` и присоединяет даты как `ActivityDateBegin` / `ActivityDateEnd`. Не переноси этот consumer вместе с producer без необходимости.

В исходных runner/YQL не обнаружена явная публикация отдельного пользовательского Reactor-артефакта. Проверь фактическую обвязку, прежде чем делать вывод об отсутствии событий. Не придумывай обязательный publisher или новый namespace. Если обнаружатся существующие события и consumers, сохрани тип, payload, дату, namespace и момент публикации после commit.

## 10. Проверки поведения

Перенеси существующие `test_init` и `test_update`, fixtures, YSON-данные и каноны из `bin/test/` на принятый локальный запуск Logos через Uty/TaskRunner и `tests.yt_test_func`. Пути получай из TaskRunner, а не из production-конфига. Не ограничивайся тестами `dependencies()` или списков классов.

Не создавай отдельный тяжёлый тест на каждый пункт: сгруппируй совместимые сценарии и расширь существующий E2E. Нужны содержательные проверки:

| Сценарий | Что доказать |
|---|---|
| Init без activity | Результат, схема, сортировка и атрибуты соответствуют прежним канонам; читаются обе архивные ветки |
| Init при наличии текущих вершин | В bootstrap не добавляются строки текущего snapshot сверх legacy-логики |
| Update существующей activity | Сохранение старых минимумов и обновление максимумов |
| Новый / исчезнувший / вернувшийся ID | Добавление нового, сохранение отсутствующего, продолжение истории |
| Дубликаты и пустые ID | Корректная агрегация и прежняя фильтрация |
| Одинаковый generate_date | YQL не запускается; строки и legacy-атрибуты не меняются, включая обвязку Logos |
| Дата попытки отличается от даты входа | `run_date` и `generate_date` не смешиваются с `ctx.task_dt` |
| Повтор в том же Python-процессе после границы UTC-дня | Время новой попытки вычисляется заново |
| Ошибка записи/YQL | Старое накопленное состояние и его атрибуты сохраняются |
| Retry после ошибки | Успешный повтор не теряет историю и не плодит строки |
| Подмены путей | Вершины, output-state, архивы и tmp используют изолированные адреса; production не изменяется |
| Исторический или запрещённый режим | Проверяется выбранная политика до побочных эффектов |

Проверяй неизменяемые входы через `TableIsNotChanged` на фактических путях. Для обновляемой `activity` проверь ожидаемый результат как состояние, которое изменяется намеренно.

Rollback доказывай исполнением с реальной локальной транзакцией и YQL. Тест, в котором весь SQL заменён mock, не подтверждает атомарность записи. При невозможности запуска на текущей платформе укажи точную границу проверки, сохрани runnable tests и не называй их выполненным E2E.

Не меняй канонические данные ради того, чтобы приспособить новую обвязку к другой семантике. Если канон действительно должен измениться, объясни причину и регенерируй штатным runner, не редактируй вручную.

## 12. План переключения и отката

Подготовь конкретный порядок действий, не выполняя его на production в рамках этой задачи:

1. Проверить доступы effective execution owner к Kolmogorov, входам, state, архивам и tmp.
2. Проверить отношение production/public-путей и существующее содержимое `activity`; определить безопасное резервирование накопленного state перед переключением.
3. Сравнить legacy и Logos на **одних зафиксированных входах и копии одинакового начального state**, в разных изолированных выходах. При необходимости сравнения запускать его в разрешённой тестовой среде, не над live-state.
4. Убедиться, что регистрация и автоматический релиз нового графа не включат второго writer раньше остановки старого.
5. Отключить нужный старый scheduler и дождаться завершения/снятия его running и queued attempts, YT-операций и транзакций.
6. Включить новый запуск с существующей историей; проверить выбранный первый слот, входной `generate_date`, результат, атрибуты, public-путь и потребителя BigB.
7. Проверить мониторинг и отсутствие двух writers. Для testing выполнить отдельный предусмотренный переход; если PREPROD не действует, не оставлять testing без прежнего запуска.
8. Для отката сначала остановить Logos writer и его активные операции, затем вернуть совместимый legacy-запуск. Историю `activity` не удалять и не откатывать слепым cold start.

Проверь, какие legacy CLI/bundle/config/Spine-модули действительно стали не нужны. Удаляй их и сборочные ссылки после проверки consumers и с учётом согласованного способа отката. Общие вычисления и SQL сохраняй, если ими пользуется новая задача.

Разделяй мониторинг старого scheduler и свежесть данных. Не удаляй работающую проверку без действующей замены; `49h` не объявляй порогом свежести графа. Не создавай новые alert-пороги без основания.

Порядок cutover и rollback помести в итоговое описание изменений или отдельный reviewable документ. В пользовательский README не добавляй историю переписки и длинный пересказ runtime-конфига.

## 13. Критерии готовности и итоговый ответ

Миграция кода готова к ревью, если:

- реализован один расчёт activity в нужном Logos-проекте и явно описаны окружения;
- сохранены paths/aliases, схема, sort key, optionality и накопленное состояние;
- сохранены init/update, идемпотентность по `generate_date` и различие всех дат;
- пути берутся из поддерживаемых bindings и изолируются в тестах/dev;
- определены владелец транзакции, no-op-поведение, ограничения writers и допустимые режимы запуска;
- подтверждены функциональные результаты, атрибуты и rollback в доступной среде;
- обновлены build, graph, release discovery и требуемые Spine-конфигурации/каноны;
- интерфейс public activity и потребители сохранены либо изменение явно выделено и согласовано;
- подготовлены проверяемые шаги переключения и отката;
- production не переключён и persistent state не пересоздан в ходе подготовки diff.

В итоговом ответе сообщи:

1. Какие файлы и задачи изменены, куда зарегистрированы production/testing.
2. Выбранные зависимости, логтайпы, даты, транзакционный механизм и effective runtime settings.
3. Что полностью сохранено и какие изменения поведения оказались необходимы.
4. Какие команды и E2E действительно выполнены, с какими результатами; что осталось непроверенным.
5. Что требуется для cutover, как исключён второй writer и как выполнить rollback.
6. Какие конкретные вопросы остались нерешёнными и почему их нельзя было разрешить по доступным источникам.

Не создавай commit, push или PR без отдельного запроса на эти действия. Не выполняй production-переключение, не запускай live-пересчёт и не отправляй сообщения другим людям в рамках подготовки миграции. Заверши работу конкретным кодом и проверяемым diff, а не только планом.
